## What changed in Week 3 (read this first)

- **Tuesday value verification moved *out* of In-Class Activities and *into* the Final Project** as **Checkpoint 1**. It is now **group-graded**, not an individual activity.
- **Monday usability testing stays an individual In-Class Activity** (the ≤5-min video + reflection).
- The **Final Project now runs Tue → Thu as four graded checkpoints** — you grade the group four times, and the summary is the grade.

So in Week 3 the **only** In-Class Activity is **Monday 7/27**; Tue/Wed/Thu are all Final-Project checkpoints.

| # | Day | Deliverable(s) | Where |

**How the checkpoints roll into the weights:**
- **Checkpoints 1–3 → the 25% Final Project grade** (assessed against the Project Rubric).
- **Checkpoint 4 → the 15% Final Presentation grade.**

**Project Rubric mapped across the days** (so each checkpoint scores part of the 25%):

| Rubric component | Weight | Mostly earned on |
| :--- | :--- | :--- |
| Good Vibes — Concept & Planning | 20% | Tue verify + Wed plan |
| Good Code — Functionality & Execution | 20% | Thu build |
| Live Demo — User Testing | 15% | Tue verify (+ Thu quick test) |
| Deep Ethical Reflection | 25% | canvas reflection lanes + `project-report.md` (human-written) |
| Communication & Documentation | 20% | deck + report + the team **overview page** (`code_deliverable/overview.html`) |

**Individual accountability inside the group grade:** the Tuesday deck has a **named slide per member** and the canvas a **named reflection lane per member**; together with git history and the AI log, these inform the anonymous **[peer-check](../projects/peer-check.md)**. Team grade by default — split out an individual only in exceptional cases.

## In-Class Activities (20%) — individual

Averaged across every daily activity (Weeks 1–3). Each is scored 0–100 against the
[Activity Rubric](activity_rubric.md) (40 Completion · 30 AI-Use · 30 Reflection). In **Week 3**,
the only activity is **Monday 7/27 — Usability Testing** (video + reflection).

## Canvas setup — assignment groups

Create **weighted assignment groups** matching the breakdown, then add the assignments:

| Assignment group (weight) | Assignments inside | Type |
| :--- | :--- | :--- |
| **In-Class Activities (20%)** | one per daily activity (incl. Mon 7/27) | Individual, 0–100 |
| **Project 1 (15%)** | Project 1 | Group |
| **Project 2 (15%)** | Project 2 | Group |
| **Final Project (25%)** | Checkpoint 1 · Checkpoint 2 · Checkpoint 3 | **Group** |
| **Final Presentation (15%)** | Checkpoint 4 | **Group** |
| **Participation (10%)** | participation | Individual |

- Make the four Final checkpoints **Canvas Group Assignments** tied to a **group set = the final teams**, so one grade applies to the whole team.
- Weight the *group*, not each checkpoint — Canvas averages the checkpoints within the 25% Final Project group automatically. (If you want the three build-up checkpoints weighted unequally, give them different point values.)
- The **peer-check** is a separate short survey; use it to adjust individuals only in exceptional cases.

## Policies (from the syllabus — apply to everything)

- **Team grade by default** for group work; individual grades only in exceptional cases with strong justification (git history + AI log + peer-check inform the call). Raise contribution problems *during* the project.
- **Late / incomplete / misformatted work does not earn full credit;** commits after the time in `deadline.json` don't count. Running out of AI credits is not an excuse.
- **Submission via GitHub Classroom only** (+ the Canvas link) — work a grader can't find may be graded as missing.
- **One regrade per item, within 24 h of release;** a *different* instructor regrades and **that grade stands**.
- **AI writing is impermissible in reflections** (ethical + individual), grammar checking only.
